# 🥦 Kurly Clone Backend (E-Commerce Backoffice & WMS)
입고·출고·주문이 동시에 발생하는 상품 · 물류 환경에서 락-프리(Lock-Free) 동시성 제어로 재고 정합성을 확보하고, 추가 인프라 없이 기존 DB 내장 기능만으로 검색 성능을 극대화한 백엔드 시스템입니다.

### 🎯 Project Background: 왜 WMS까지 구현했는가?
>서비스의 핵심 가치를 분석했을 때, 마켓컬리의 본질은 단순 이커머스가 아닌 **신선식품을 빠르고 정확하게 처리하는 물류 풀필먼트(Fulfillment) 시스템**에 있다고 판단했습니다. 

이에 따라 인증·상품·주문/결제 중심의 프론트 오피스(Front-Office) 구현에 그치지 않고, **WMS(창고관리), OMS(주문관리), SCM(공급망관리)으로 이어지는 백오피스 도메인까지 아키텍처를 확장**하여 설계했습니다. 저는 이 중 **상품 및 WMS 도메인**을 전담하며, 단순 CRUD를 넘어 입고부터 적치, 주문 선점, 출고로 이어지는 실제 물류 흐름과 데이터 정합성을 구현하는 데 집중했습니다.

> - 진행 기간: 2026.08 ~ 2026.10 (3개월)
> - 팀 구성 & 역할: 백엔드 3인 / 전체 22인 (상품 · 재고(WMS) 도메인 설계 및 성능 최적화 전담)
> - 핵심 기술: Spring Boot, PostgreSQL, Redis, RabbitMQ, Lua Script, `pg_trgm` & GIN Index, TypeSpec, Flyway
> - 핵심 검증: Redis Lua Script 기반 동시 100건 요청 초과 선점 `0건`(`p95 15ms`), `pg_trgm` + GIN 인덱스로 부분 일치 검색 속도 최대 약 `18배` 개선, TypeSpec 기반 API 명세 자동화 구축

## 1. 분산 락 대신 Redis Lua Script로 구현한 락-프리(Lock-Free) 원자적 재고 선점

### [문제 현상 및 배경]
- 입고·출고·주문 트랜잭션이 동일한 상품 재고를 동시에 수정하는 물류(WMS) 도메인 특성상 동시성 이슈 발생 위험 존재.
- RDBMS 비관적 락은 디스크 I/O 병목을 유발하고, Redisson 분산 락은 **락 획득·해제 과정의 반복적인 네트워크 왕복(RTT)과 애플리케이션 스레드 대기 오버헤드**로 리소스 부담과 인프라 운영 비용 증가 우려.

### [해결 전략 및 아키텍처]

1. **인프라 비용 최적화를 위한 Redis 단일 스레드 기반 락-프리(Lock-Free) 연산 채택**
   - 인프라 팀의 운영 비용 절감 기조에 맞춰 별도 락 매니저나 스펙 증설 없이, 명령어를 순차 실행하는 Redis 단일 스레드 아키텍처를 활용해 락 없이(Lock-Free) 원자성을 보장하는 설계 채택.
   <br>
   <img width="1854" height="776" alt="Redis Lua Script 기반 재고 선점 흐름" src="https://github.com/user-attachments/assets/3ea51af7-6c1d-4c58-9809-9c5565b3efe5" />

2. **Lua Script를 통한 3단계 재고 선점(`Hold`) 원자 실행**
   - 주문 서버에서 요청 시 전달한 `reservationToken`(UUID)을 기준으로, 아래 3단계 검증 및 갱신 로직을 단일 Lua Script(`stock_hold.lua`)로 묶어 Redis 엔진 내부에서 원자적으로 실행.
     1) **멱등성 검사**: 주문 서버로부터 전달받은 동일 `reservationToken` 중복 요청 필터링
     2) **다중 상품 가용 수량 검증**: 주문 내 모든 상품의 `available_quantity` 충족 여부 일괄 확인
     3) **재고 선점(Hold)**: 전체 충족 시에만 각 상품의 `reserved_quantity` 증가 처리
   - 네트워크 왕복을 단 1회로 압축하여 락 경합과 스레드 대기 비용 원천 제거.

3. **논리 확정과 물리 차감 분리 및 이중 회수 안전장치**
   - **결제 완료 시 논리 재고 확정(`Confirm`)**: 주문 서비스가 `PAID` 전이 후 비동기 이벤트를 발행하면, 상품 서비스는 **DB 인박스(`INVENTORY_CONFIRM_REQUESTED + reservationToken`)**와 **Redis 예약 토큰(`HOLD → CONFIRM`)**을 함께 검증해 중복 확정을 차단하고 DB `reserved_quantity`에 주문 몫 반영.
   - **선점 해제(`Release`) 및 복구 스케줄러**: 1차적으로 주문 서버의 만료(15분)시간이 되면 취소 요청을 통해 `RELEASE` 상태로 전이(TTL 20분)하여 선점을 해제하며, **주문 서버 오류나 네트워크 유실로 해제 요청이 누락될 경우를 대비해 오래된 `HOLD` 선점을 주기적으로 회수하는 복구 스케줄러**를 운영해 미결제 점유(Ghost Reservation) 방지.

4. **Redis 휘발성에 대한 아키텍처 트레이드오프 (비용 효율 vs 영속성)**
   - **의도적 비영속(In-Memory) 유지 근거**: 이커머스 특성상 장바구니·주문서 진입 유저의 **80% 이상이 실제 결제까지 도달하지 않고 이탈**하므로, 임시 선점 상태까지 유실 방지를 위해 별도 MQ를 발행하거나 RDB에 영속화하는 것은 본래의 **인프라 운영 비용 절감 목표에 어긋난다고** 판단. 또한 임시 선점 정보는 반드시 영구 보존해야 할 핵심 원장 데이터가 아니므로 인메모리 처리 유지.
   - **휘발 시 정합성 방어**: 최초 재고 확정은 Redis에 HOLD 상태의 예약 토큰이 있어야 성공. 선점 정보가 유실되어 토큰을 확인할 수 없으면 예외 처리하여 선점 없이 재고가 확정되는 것을 방지한다. 이미 확정이 커밋된 요청은 DB 인박스 테이블로 중복 처리를 차단한다.

### [검증 결과]
- **동시성 및 정합성 검증**: 7개 핵심 경합 시나리오(동시 100건 요청 부하 환경)에서 **초과 선점 0건, 수량 정합성 100%** 달성.
- **응답 지연 최적화**: 락 대기와 다중 네트워크 I/O를 제거하여 일반 동시 요청 시 **`p95` 50~61ms**, DB Lazy Sync가 수반되는 콜드 캐시 환경에서도 **`p95` 130.53ms**의 일관된 저지연 처리 확보.

| # | 시나리오 | 동시 요청 조건 | 검증 결과 | `p95` 응답 시간 |
| :-: | :--- | :--- | :--- | :---: |
| **1** | **재고가 충분한 동시 선점** | 재고 200개에 100건이 각 2개 선점 | 전부 성공, `reserved_quantity`가 정확히 200 | **51.23ms** |
| **2** | **재고 부족 상황에서 초과 선점 방지** | 재고 30개에 100건이 각 1개 선점 | 30건만 성공, 70건은 재고 부족 실패 (예약 수량 30) | **61.50ms** |

> **💡 테스트 환경 및 수치의 기술적 의의**  
> - **측정 환경**: Windows 개발 환경에서 Docker Compose(Redis·RabbitMQ) 및 로컬 PostgreSQL을 기반으로, 100개 스레드를 동시에 실행해 **서비스 메서드 단위의 실행 시간**을 단회 측정한 결과입니다. (HTTP 네트워크 왕복 오버헤드 및 실제 분산 운영 환경의 장시간 지속 부하는 미포함)  
> - **수치 해석 기준**: 7번(콜드 캐시) 시나리오는 캐시 미스 이후 **DB 조회 및 Redis 캐시 초기 적재(Lazy Sync) 비용까지 모두 포함된 수치**이므로, 이미 캐시가 적재된 상태(1~6번)의 Lua Script 순수 실행 성능과 직접 비교하지 않고 초기 적재 구간의 정합성·지연 검증 지표로 구분하여 해석했습니다.  
> - **로컬 환경 검증의 의의**: 단일 머신의 제한된 리소스 경합 환경에서 측정된 수치임에도, **100개 스레드가 동일 키에 동시 충돌하는 극한 경합 조건에서 초과 선점 0건(정합성 100%)을 보장**했으며, 스레드 대기나 락 경합으로 인한 꼬리 지연(Tail Latency) 급증 없이 **모든 캐시 적중 시나리오가 일관되게 `p95` 50~61ms 범위 내에서 안정적으로 수렴**했다는 점에서 락-프리(Lock-Free) 설계의 실효성을 충분히 입증하는 의미 있는 지표입니다.

## 2. 검색 엔진 도입 없이 `pg_trgm` + GIN 인덱스로 부분 일치 검색 최대 약 18배 개선

### [문제 현상 및 배경]
- 상품명 중간 키워드 매칭(`LIKE '%검색어%'`) 요구사항에서 일반 B-Tree 인덱스를 활용할 수 없어 매 조회마다 **Full Table Scan(`Seq Scan`)** 에 의존.
- 상품 데이터가 누적됨에 따라 조회 응답 시간이 선형적으로 증가할 위험 존재.
- 서버 리소스와 운영 비용 제약으로 Elasticsearch 등 별도의 외부 검색 엔진 인프라 도입이 어려운 환경.

### [해결 전략 및 아키텍처]
1. **`pg_trgm` 확장 모듈을 활용한 Trigram 토큰화**
   - 신규 인프라를 추가하는 대신 기존 PostgreSQL 내장 자원을 극대화하는 방향으로 의사결정.
   - 문자열을 3글자 단위(Trigram)로 분해해 인덱싱하는 `pg_trgm` 확장을 활성화하여 중간 문자열 검색 기반 마련.

2. **GIN(Generalized Inverted Index) 역색인 구조 구축**
   - 다중 Trigram 토큰을 효율적으로 역색인할 수 있도록 상품명 컬럼에 GIN 인덱스를 생성하고, 부분 일치 검색 쿼리가 역색인을 타도록 최적화.

### [검증 결과 및 실행 계획 분석]
실데이터 10만 건 환경에서 검색어의 길이와 구체성(선택도)을 달리한 3가지 케이스로 `EXPLAIN ANALYZE` 실행 계획 및 응답 시간을 비교 검증했습니다.

- **실행 계획 전환**: 모든 부분 일치 검색 쿼리에서 테이블 전체를 읽던 `Seq Scan`이 **`Bitmap Index Scan` + `Bitmap Heap Scan`으로 전환**됨을 확인.
- **조회 성능 향상 및 검색어 특성 분석**:
  - 부분 일치 검색 쿼리 응답 속도를 **최대 약 18배 개선**하여 별도 검색 엔진 없이도 수 ms 단위의 안정적인 응답 확보.
  - 특히 `'바나나'`처럼 짧고 보편적인 키워드보다 **`'제주 바나나'`처럼 더 길고 구체적인 검색어일수록 생성되는 Trigram 토큰 교집합이 많아져 인덱스 선택도(Selectivity)가 높아지고, 이에 따라 후보 행(Heap Block) 접근량이 크게 줄어들며 성능 개선 폭이 더욱 극대화**됨을 확인.

## 3. TypeSpec 기반 API 명세 표준화와 Agentic AI 개발 파이프라인 구축

### [문제 현상 및 배경]
- **스펙 불일치와 수작업 비용**: 백엔드 코드와 API 문서 간 스펙 불일치로 프론트엔드·백엔드 간 커뮤니케이션 비용이 반복되고, 변경된 DTO와 문서를 수동으로 갱신하며 개발 생산성 저하.
- **AI 에이전트 활용의 한계**: 코드 생성 시 AI 에이전트가 참고할 표준화되고 구조화된 단일 명세가 부재해, 개발 의도와 어긋난 코드나 환각(Hallucination)이 발생하는 한계 존재.

### [해결 전략 및 아키텍처]
1. **TypeSpec 기반 스키마 및 API 인터페이스 표준화**
   - API-First 설계를 위해 간결하고 정형화된 스키마 언어 **TypeSpec**을 단일 진실 공급원(SSOT)으로 도입하여 API 엔드포인트와 DTO 데이터 모델을 표준화.
   <!-- TypeSpec 명세 작성 예시 또는 CI 자동화 파이프라인 흐름도 위치 -->

2. **Agentic AI 기반 구현 전 사전 명세 검토**
   - 정제된 TypeSpec 명세를 Agentic AI에 컨텍스트로 제공하여, 실제 백엔드 구현에 들어가기 전 AI와 함께 누락된 예외 케이스, 필드 제약 조건, 스펙 결함을 사전에 검증.

3. **CI 기반 Notion API 문서 자동 동기화 파이프라인**
   - PR 머지 시 변경된 TypeSpec 스키마를 파싱해 팀 Notion 명세 페이지에 자동 반영하는 CI 파이프라인을 구축함으로써, 별도 수작업 없이 문서의 최신성을 상시 보장.

### [개선 성과]
- **스펙 불일치 차단 및 문서화 자동화**: 개발 전 AI 명세 검토부터 개발 후 CI 기반 자동 문서 갱신까지 하나의 흐름으로 연결하여, 수동 문서 갱신 비용을 제거하고 프론트-백엔드 간 스펙 불일치 원천 차단.
- **AI 코드 생성 품질 및 생산성 향상**: 모호함이 제거된 최신 스키마를 AI 에이전트에 공급하여 오류 코드 생성을 방지하고, 표준화된 명세 기반의 DTO 및 비즈니스 로직 구현 속도 개선.
- **병렬 개발 환경 확보**: 신뢰할 수 있는 최신 명세를 기준으로 백엔드 구현 완료 전에도 프론트엔드 Mocking 환경을 즉시 구축해 팀 단위 병렬 개발 실현.

## 협업 규칙

- 기본 브랜치는 **`develop`**. 브랜치 이름은 `feat/auth-init#6`처럼 `타입/설명#이슈번호`
- 커밋 메시지는 **한국어**. `feat:` `fix:` `docs:` `chore:` + 설명
- PR·이슈·코드리뷰 모두 한국어 기준이다
- CodeRabbit 리뷰는 오버엔지니어링·중복·불필요한 의존성·Spring Boot 4 / Gradle 9 비호환을 중점적으로 본다.
  **현재 요구사항 이상으로 추상화하지 않는다**

### 서비스 담당

서비스마다 담당자가 있다. 전체를 훑는 작업이라도 **담당 서비스만 고치고 나머지는 인계 항목으로
보고한다.** 불가피하게 다른 영역을 건드렸다면 PR 본문에 그 사실과 확인이 필요한 지점을 적는다.
